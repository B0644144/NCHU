## 建議定位

這張圖不要講成「我重寫了一套 TREK Lite 系統」，而是講成：

> 左側是我選擇 TREK 這個 GitHub 開源專案的原因，右側是我這次把日本滑雪 Notion 行程整理進 TREK 後的實作成果。

這樣會更貼近今晚報告主軸：介紹如何使用 TREK GitHub 專案，到整理資料並做出可展示的旅行規劃系統。

## 45 到 60 秒口白

> 這張圖左邊是 TREK 原本作為旅遊管理系統的核心優勢，包含行程、地圖、預算、打包清單與文件管理。這也是我選擇它作為基礎的原因。右邊則是這次我的實作案例：我把 Notion 裡的日本滑雪行程轉成系統化資料，包含 2026-02-26 到 03-04 的行程、地圖點邏輯、47 筆旅行物品清單，以及 62 筆費用記錄。接下來 Demo 我會直接展示這些資料在 TREK 裡面實際呈現的樣子。

## 使用重點

- 左側講「為什麼選 TREK」。
- 右側講「我這次做出的案例」。
- 不需要深入解釋 React、Node.js、SQLite、WebSocket、PWA、MCP。
- 如果被問到技術，可以簡短回答：「這些是 TREK 原專案提供或支援的架構能力，我這次報告重點放在如何導入專案並整理實際旅行資料。」
